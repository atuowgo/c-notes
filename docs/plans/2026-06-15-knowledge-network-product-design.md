## 1. 产品定位与核心洞察

**一句话定位**:一个面向中文重度阅读者的"个人知识炼金炉"——把你在浏览器、微信公众号、知乎等多个渠道收集的零散文章,自动织成一张有结构、会生长的知识网,并支持批注和与 AI 深聊,让"收藏"真正变成"你自己的知识"。

**目标用户(先是作者自己)**:跨多个中文渠道高频阅读、有收藏习惯、但苦于"收了等于没收"——内容散、读不完、更整理不出沉淀的人。

**产品路线**:自用优先,但有产品潜力(架构留扩展空间,MVP 先服务自己)。

### 核心洞察 / 差异化

市面产品各做了一段,但没人打通这条链:

- **Pocket / Instapaper**:擅长"收 + 读",但不懂组织,更不碰中文微信生态。
- **Notion AI**:能归类摘要(AI Autofill 可自动填摘要/标签字段),但收集是"原样存"、进不来微信、且**不会主动组织**。
- **真正的空白地带** = **"自动组织成知识网" + "中文多源无摩擦收集"**——这两点恰是别人最弱、作者最痛的地方,也是本产品的护城河。

### 产品信条(贯穿设计的原则)

1. **收集零摩擦**——任何渠道,一个动作就进来,绝不让你"为了整理而中断阅读"。
2. **组织自动化**——整理是系统的事,不是你的事;你醒来知识网已经长好了。
3. **沉淀可对话**——知识不是死的存档,是能被追问、被批注、被深聊的活体。

## 2. 核心链路与用户旅程

整个产品是一条**从"信息进来"到"变成你的知识"的流水线**,分五个环节:

| 环节 | 触发方式 | 说明 |
|------|----------|------|
| **① 收集 Capture** | 主动,零摩擦 | 微信转发链接 / 浏览器插件一点;两秒完成,不中断阅读。 |
| **② 自动组织 Organize** | 异步自动 | 抓正文、去广告、识别主题,把内容挂到知识网的合适位置,更新主题脉络。 |
| **③ 自动沉淀 Distill** | 异步自动 | 每篇生成摘要 + 要点;每个主题簇生成并持续更新"演进式综述"。 |
| **④ 批注 Annotate** | 主动 | 阅读时划线、写想法。**基础版(划线 + 想法 + 浏览)已提前进 MVP 阅读端**(见 6.4);"批注成为知识网一等节点"留到 V4。 |
| **⑤ 深聊 Converse** | 主动 | 基于多源检索与 AI 对话(见下)。 |

**关键设计点**:②③ 是**异步自动**发生的(你睡觉时系统在工作),④⑤ 是**你主动触发**的。前者是"省心",后者是"增益"。这呼应"醒来知识网已经长好"的体验目标。

### 深聊的三层知识来源(双引擎检索)

AI 深聊不封闭在私域库里,知识来源分三层:

1. **这篇文章本身**(最近上下文)。
2. **你知识网里的相关内容**(私域积累——比通用 ChatGPT 更懂你)。
3. **联网检索的外部内容**(补你库里没有的最新/权威信息)。

> **AI 深聊 = 私域知识网 + 实时联网,双引擎检索。** 通用 AI 不懂你的私域,纯收藏工具不会联网深聊,本产品两者兼得。

**衍生机会(已纳入设计,可后续按需取舍)**:深聊中联网发现的好内容,可**一键收进知识网**——让"聊"反过来成为"收"的入口,链路自我闭环。

## 3. "自动组织成知识网"的具体形态

**知识网 = 主题簇(Cluster)+ 关联(Link)+ 演进式综述(Living Summary)**

- **主题簇**:系统按语义自动把文章聚成主题(如"LLM 推理优化""个人知识管理"),无需手动建文件夹;一篇可属于多个簇。
- **关联**:文章↔文章、文章↔批注之间,自动生成"为什么相关"的连线(引用同一概念、观点对立、互为补充等)。
- **演进式综述**:每个簇有一篇 AI 维护的"活综述",随新内容自动重写——是回顾一个主题时的入口。参考 Karpathy LLM Wiki 思路:不是简单罗列,而是把多篇织成一篇有逻辑的概览。

**关键产品决策——自动为主、可轻量纠偏**:全自动聚类常"聚得不是你想要的"。采取系统先聚好、用户可合并/拆分簇、可把某篇拖到别的簇,系统记住偏好。既省心,又不失控。

## 4. MVP 与演进路线

**排序原则**:每个阶段都必须是一条**端到端能用**的切片(收得进、看得到),而非先憋后台。先让自己每天用起来,在真实使用里验证下一步该加什么。

### MVP — "收进来 + 自动归类摘要 + 能读"(证明核心魔法)

- **收集**:先做**浏览器插件**一个渠道(技术最稳,覆盖电脑长文场景)。
- **自动**:抓正文 → 生成摘要/要点 → 自动打主题标签(先做标签,不做完整知识网)。
- **读**:一个 **Web 阅读端**,收件箱 + 清爽正文 + 自动沉淀;含**划线记想法**(批注基础版)与深聊入口外壳(详见第 6 节,原型已落)。
- **验证目标**:"无摩擦收 + 自动摘要"是否真的天天愿意用。

### V2 — "微信收集"(补齐最痛的入口)

- 加微信入口(转发链接即收)。技术最难、价值最高,单独作为里程碑,与"证明核心魔法"解耦,避免一上来卡在最硬的骨头上。

### V3 — "从标签长成知识网"(自动组织)

- 主题簇 + 关联 + 演进式综述;移动端阅读。

### V4 — "让知识活起来"(沉淀与深聊)

- 批注**升级为知识网一等节点**(批注↔文章、批注↔批注自动关联);AI 深聊真正接上私域知识网 + 联网双引擎。
- *注:划线/想法基础版与深聊入口外壳已在 MVP 阅读端落地(见 6.4 / 6.5),V4 是把它们从"本地笔记 + 交互示意"升级为"真正可检索、可对话、入网"的完整能力。*

**形态结论**:多端场景(手机收微信、电脑读长文,两端都能收能读)决定架构必为"云端后台 + 多个轻客户端(浏览器插件、微信入口、Web、移动端)+ 实时同步"。

## 5. MVP 技术架构(第二轮脑爆产出)

### 5.1 总体取向:托管但可迁移(方案 A)

现在"怎么省事怎么来",但每个选择都保留"将来能搬家"的余地:MySQL 标准表结构、正文存通用 Markdown/JSON、模型走抽象层。既快速起步,又不把自己焊死在某个云/某个模型上——呼应隐私选项 C(本地/自托管/数据可控 作为待评估选项保留)。

### 5.2 部署形态:单机常驻服务,预留多机

**MVP — 单机**:一台云服务器(轻量应用服务器,约 ¥24–60/月)上跑:
- 一个**常驻后端服务**(Node/Python/Go 均可),对外暴露 HTTP 接口;
- **MySQL 装在同机**(将来量大再拆到托管 MySQL);
- 图片/正文快照等存**对象存储**(MVP 也可先落本地磁盘)。

插件、微信回调**直连本服务器**,无云函数中转(`/collect` 收插件,`/wechat/callback` 收微信,写入同一张 `article` 表,靠 `source_type` 区分)。

**为什么不用 Serverless**:自用场景下 Serverless 同样按调用付费,而自己一台服务器掌控力更强、能常驻跑无头浏览器、无冷启动、便于自托管迁移。

**预留多机的五条原则**(MVP 零成本预留,将来不返工):
1. **后端无状态**:登录态走 token/JWT、文件走对象存储,不依赖本地状态 → 将来可多开 + 负载均衡。
2. **收/发逻辑分离**:接收(`/collect`)与处理(Worker)在代码上拆成两个模块,将来抽成两进程/两机。
3. **任务投递抽象一层**:MVP 用"写 DB + 轮询",将来换消息队列只改这层。
4. **MySQL 连接走配置**:`host/port` 配置化,同机为 `localhost`,将来指向托管 MySQL 只改配置。
5. **文件走对象存储**:不写本地磁盘,避免多机时文件不共享。

### 5.3 数据流:先入库后处理(异步)

1. `/collect` 收到提交 → 写 `article(status=pending)` → **立即返回**(不阻塞阅读)。
2. **后台 Worker**(常驻线程/定时循环)扫 `pending` → 抓正文 → 生成摘要/要点/标签 → 置 `done`。
3. **状态机**:`pending → processing → done / failed`;失败按指数退避重试。
4. **省 round-trip**:摘要 + 要点 + 标签**合并为一次模型调用**(要求 JSON 输出),一次拿全。

常驻进程的红利:**无头浏览器(第 3 级抓取)直接跑在这台机器上**,无云函数体积/冷启动限制。

### 5.4 三级正文抓取(成本由低到高,逐级兜底)

1. **插件本地 Readability 提取**(近免费):读浏览器里**渲染后的 DOM**,天然处理 SPA 动态渲染;`all_frames` 覆盖 iframe;能拿到用户**已登录/付费墙内可见**的内容。
2. **模型清洗渲染后 DOM 快照**(中等成本):插件附带 DOM 快照,正文提取不干净时由模型清洗兜底。
3. **服务器无头浏览器渲染**(重):处理裸 URL、强动态页、跨域 iframe、微信 V2。诚实盲区:看不到用户登录态、可能被反爬拦截。

插件提交载荷:`url / title / content(本地提取正文) / dom_snapshot(兜底) / source_type`。

### 5.5 数据模型

**全表统一标准**:
```sql
id          CHAR(32)    NOT NULL,            -- 32 位 UUID hex,应用生成
-- ... 业务字段 ...
create_time DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (id)
```
每表另有**业务唯一索引**(长字段用 `xxx_hash CHAR(32)` 落索引)。

**5 张 MVP 表**:
- `article`:`uk_url_hash(url_hash)`;字段含 `url / title / author / source_type / content(Markdown) / summary / key_points(JSON) / status / extract_method / processed_at`。
- `tag`:`uk_name`;字段 `name / description`。将来长成簇:加 `parent_id / living_summary`。
- `article_tag`:`uk_article_tag(article_id, tag_id)`;带 `confidence`。
- `tag_suggestion`:`uk_article_name(article_id, name)`。
- `note`(划线/想法,见 6.4):`article_id`(外键)/ `quote`(划线引文)/ `thought`(想法,可空)/ `anchor`(JSON,正文定位信息,如 selector + offset,用于将来重新高亮)。按 `idx_article_id` 查询。**无天然业务唯一键**(同一段可被重复划线、写不同想法),此处作为建表规范的合理例外——仅保留物理主键 `id`;是否引入 `anchor_hash` 去重待实现时再定(见第 8 节)。

### 5.6 标签:受控标签集 + AI 归类(方案 B)

AI **从既有 `tag` 里选**,选不准的新标签写入 `tag_suggestion` 待确认后才转正,避免全自由打标导致标签爆炸。这是 V3 "标签长成知识网"的种子。

### 5.7 模型抽象层

模型/厂商收敛在一处可整体替换:**便宜档**跑批量组织(抓取/摘要/打标),**聪明档**留给 V4 深聊。便于成本控制与隐私选项 C 下的"换自托管模型"。

## 6. MVP Web 阅读端(第三轮:原型已落地)

> 对应可点击原型:`docs/prototype/web-reader.html`。视觉基调:琥珀金 + 暖中性,760px 阅读宽度。本节是该原型的设计说明,实现细节待开发时细化。

### 6.1 形态:收件箱为主 + 标签筛选为辅(方案 C)

主视图是一条**收件箱卡片流**(按"今天 / 昨天"分组),标签栏置顶做二级筛选。呼应信条"收集零摩擦、组织自动化"——阅读端默认按时间倒序的收件箱,不强迫用户先归类。

### 6.2 卡片(列表项)

标题 + 来源·作者·时间 + 两行摘要 + 标签 + 状态角标。三种状态直接对应异步流水线(5.3):**处理中**(骨架屏 + 脉冲点)、**已就绪**、**失败**(红角标 + 重试)。已读卡片自动变灰。

### 6.3 正文阅读页

自上而下:返回 / 本文想法入口 → 标题 → 来源·作者·看原文 → **标签(置顶)** → **自动沉淀卡**(摘要 + 要点)→ 清爽正文 → **推荐文**。

- **自动沉淀**:5.3 节"摘要 + 要点"的展示位。
- **推荐文**:顺着本文延伸,分"相关 / 更深入"两类。MVP 可先用标签 + embedding 近邻粗排;V3 知识网成型后改由簇 / 关联驱动。

### 6.4 划线记想法(批注基础版,从 V4 提前)

原型把"批注"拆出一个**可独立使用的基础版**放进 MVP 阅读端:

- **划线**:选中正文任意片段 → 浮出"划线记想法" → 高亮 + 弹气泡写想法(可仅划线、不写字)。
- **本文想法**:正文页顶部入口(带计数),抽屉列出本篇全部划线 + 想法。
- **全部想法**:首页顶栏入口,跨文章汇总,每条标注来源文章。
- **为问答 / 创作预留钩子**:每条想法挂"提问 / 创作"两个动作(原型占位)。设想:**提问** → 把该想法作为开场问题甩进深聊(三层来源再加一层"我的想法");**创作** → 以想法为骨架进入拼装视图。这是"想法不止是笔记,而是下一步对话与产出的种子"的落点。
- 数据落 `note` 表(见 5.5)。

> V4 的"批注"完整形态 = 让批注成为**知识网的一等节点**(批注↔文章、批注↔批注自动关联)。MVP 先落"划线 + 想法 + 浏览"这层,入网关联留到知识网成型(V3/V4)。

### 6.5 AI 深聊入口(V4 能力,原型先示意)

右下角常驻"深聊"悬浮按钮;面板支持**通用对话**与**对当前文章对话**两种上下文切换;每条 AI 回答标注三层来源(本文 / 知识网 / 联网)。MVP 阶段仅为交互外壳示意,**真正的双引擎检索是 V4**。提前放壳,是为了让"收集 → 阅读 → 对话"的闭环在原型里可感知、可验证。

## 7. 成功标准

以作者自己为衡量基准:

- **MVP 成**:连续两周,80%+ 的"想收的文章"都用它收,且每周至少回看几次摘要——说明真的进入习惯,而非又一个废弃工具。
- **知识网成(V3)**:想回顾一个主题时,**第一反应是去翻它的"活综述",而不是去搜索引擎**。
- **深聊成(V4)**:有几次,AI 因"懂你私域"给出了通用 ChatGPT 给不了的回答。

## 8. 待定决策(留到实现脑爆再敲,不阻塞产品设计)

1. **模型选型**:已定**抽象层 + 分档**策略(便宜档跑组织、聪明档管深聊);具体厂商/型号待实现时选。
2. **微信收集机制**:转发到服务号/机器人/文件传输助手等,合规与可行性 V2 专门论证(认证服务号需营业执照 + 年费,回调 5 秒响应限制——正好契合"先入库后处理")。
3. **正文抓取可靠性**:已定**三级抓取**兜底(见 5.4);公众号、付费墙、动态页的具体覆盖率待真实使用验证。
4. **想法(note)落地细节(见 6.4)**:
   - *去重*:`note` 表无天然业务唯一键(同段可重复划线写不同想法),已定**仅留物理主键**为建表规范的合理例外;是否引入 `anchor_hash` 去重待实现时定。
   - *正文重定位*:`anchor`(JSON,selector + offset)如何在正文重排/抓取更新后稳定复原高亮,待实现时验证。
   - *提问 / 创作落点*:已有设想——**提问** = 把想法作为开场问题进深聊并新增"我的想法"为第四层来源;**创作** = 想法作骨架的拼装视图。具体形态留到 V4 深聊真正接通时定。
5. **隐私(已决定:选项 C — 先记着,实现脑爆再定)**:
   - *第一层(自用)*:私人阅读内容是否经外部模型 API、数据库放自托管还是托管云——作者现在说不准,故架构上**保留"本地/自托管/数据可控"作为待评估选项,不提前焊死**。
   - *第二层(产品化后)*:涉及《个人信息保护法》、数据出境、平台规则等合规义务,自用阶段不触发,记录备查。

## 附:已对齐的关键判断

**第一轮(产品)**
- 产品路线:自用优先 + 产品潜力(B)。
- 护城河:自动组织成知识网 + 中文多源无摩擦收集。

- 数据流:先入库后处理(异步 Worker),状态机 + 退避重试,摘要/要点/标签合并一次模型调用。
- 抓取:三级兜底(插件 Readability → 模型清洗快照 → 服务器无头浏览器)。
- 数据库:MySQL;统一表标准(id CHAR(32)、业务唯一索引、create/update_time 自动时间戳);5 张 MVP 表(含 `note`)。
- 标签:受控标签集 + AI 归类(方案 B)。
- 模型:抽象层 + 分档(便宜跑组织,聪明管深聊)。

**第三轮(阅读端原型)**
- 阅读端形态:收件箱卡片流为主 + 标签筛选为辅(方案 C);正文页清爽阅读 + 自动沉淀卡 + 推荐文。
- 批注:基础版(划线 + 想法 + 浏览)提前进 MVP;本文/全部想法双入口;提问/创作留钩子。完整"批注入知识网"仍在 V4。
- 深聊:MVP 先放交互外壳(通用/本文上下文 + 三层来源标注),双引擎检索 V4 真正接通。
